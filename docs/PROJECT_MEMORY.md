## 1. Project Origin

Yalıhan AI OS originated as a bespoke real estate management portal designed for **Yalıhan Emlak**, a luxury real estate agency operating in Bodrum, Turkey. The project's core mission was to create an intelligent system capable of managing high-value villa portfolios and automating marketing activities via AI agents.

---

## 2. Business Problem

The real estate industry faces several operational overheads:
*   Manual generation and updates of listing descriptions across multiple portals (Airbnb, Sahibinden, Hepsiemlak).
*   Lack of centralized physical property records, causing description and feature drift between different portal listings.
*   Operational tracking of multi-agent tasks (e.g. photo enhancement, SEO scoring, document compliance checking).
*   Non-transparent transaction ledgers and partner allocation splits.

---

## 3. Initial Architecture

The system started as a standard Laravel-based monolithic CRUD application. In this initial stage, properties and listings were heavily coupled under the `ilanlar` table (modeled in [Ilan.php](../app/Models/Ilan.php)), and pricing, features, and media were stored directly inside the listing model.

---

## 4. Major Architectural Transitions

Over the development lifecycle, the system underwent several key transformations:

### Transition 1: Context7 Naming Authority
To enforce naming compliance, the project introduced Context7 standards. This standard mandated that all domain database columns and variables use canonical Turkish names (e.g., `aktiflik_durumu`, `display_order`), while core Laravel framework columns remained in English. A custom AST linting rule ([NamingAuthorityAstRule.php](../app/Services/Governance/Ast/Rules/NamingAuthorityAstRule.php)) was created to enforce this at the commit level.

### Transition 2: Four-Layer Operational Monolith
To support automated execution, the monolith was segmented into four clear layers:
1.  **Observation:** UI dashboard consoles.
2.  **Execution:** Hermes operating runtime and workforce queues.
3.  **Integration:** Drive Webhooks and API endpoints.
4.  **Knowledge:** Document storage metadata.

### Transition 3: Extraction of EIOS Base
As part of the platform strategy, vertical-agnostic structures were isolated into the **Enterprise Intelligence Operating System (EIOS)** layer, leaving Yalıhan OS as the primary reference implementation.

---

## 6. Superseded Approaches

*   **Static Lifecycle Bypass Flags:** Initial unit tests bypassed state machine transition guards using static properties on `YalihanLifecycle`. These were replaced by a counter-based lifecycle authorization (`$isTransitioningCounter`) in Sprint 12 to resolve cross-test data leaks.
*   **Direct Eloquent Controller Mutations:** Early controllers mutated model states directly. SAAB v11 locked down the write authority, mandating that all mutations pass through designated domain service layers (e.g., [IlanCrudService](../app/Services/Ilan/IlanCrudService.php)).

---

## 7. Successful Architectural Patterns

*   **Tenant Scoping:** The `BelongsToTenant` trait applies a global scope to all business queries, preventing cross-tenant leakage.
*   **Replay Safety:** Failures logged to workforce executions are never modified. Instead, a retry or manual replay triggers a new execution record referencing the parent UUID, preserving execution history as an immutable audit trail.
*   **Double-Entry Posting:** All balance movements in the ledger require matching debit/credit entries, maintaining algebraic consistency.

---

## 8. Business Automation Evolution

System automation progressed from basic n8n queue integrations to the implementation of the **Business Automation Index (BAI)**. The BAI measures human time savings by tracking completed workforce executions against pre-calculated manual minutes.
